## 判定: 要調整（軽微。下の問い1〜5に答えがあれば実装可）

仕様の意図と構成（データ層での分離、LLM共通部分への一本化、上限の fail closed、評価コマンド）は技術的に実現可能で、受入基準の多くはテストで確かめられる形になっている。
要調整とするのは、実装時に開発側が勝手に決めると仕様の意図を変えかねない点が5つ残っているため。いずれも推奨案（既定値）を添えたので、「推奨どおり」の一言で実装可に変えられる。
なお技術選定の承認（Q-H10）は別途必要で、承認前は実装モードに進まない（CLAUDE.md 技術選定ゲート）。

## 観点別の確認結果

### 1. 受入基準がテストで確かめられるか
概ね良好。次は補足が望ましい（判定には影響しない軽微点）。

- AC-22: 「ボタンは縦横44px以上」に、文字リンク型のボタン（「新規登録はこちら」「ログインはこちら」）を含むかが不明。提案: 含める（タップ領域が44px以上であればよい）。
- AC-9 / AC-12: 「データ層を直接呼ぶテスト」は、選定案（Postgres＋行レベルセキュリティ）ならローカルDBにBの権限で接続して実行できる。ただしローカルDBの起動に Docker が要る（architecture.md 参照）。AC-1「1コマンドで全テスト」は、そのコマンドがローカルDBの起動を含む形で実現する。品質担当の実行環境にも Docker が必要になる点を明記したい。
- AC-18: 対象は「アプリのログ」と利用記録。ホスティングやDB基盤が持つ側のログ（リクエストのログ等）は範囲外になっている。SPEC-001（相談本文の保存・送信が始まる）より前に、基盤側ログに本文が残らない設定を確認する項目が必要（下の補足A）。
- AC-8: 選定案のSupabase方式は、公式ガイドが「セッションcookieをHttpOnlyにする必要はない」としている（ブラウザ側からも読む設計）。AC-8 は HttpOnly を要求しているので、実装では「ブラウザからは基盤のSDKを使わず、サーバー側だけでセッションcookieを扱う」形にして HttpOnly を付ける。実装できるかは実装モードの冒頭で確認し、できない場合は戻して相談する（リスクとして記録）。

### 2. 未定義の挙動
問い1〜5のとおり。そのほか軽微点（開発側で既定値を置いてよいもの。architecture.md または README に記録する）:
- 月間費用の推定には「モデル別の単価」が要る。単価は設定値（環境変数または設定ファイル）に置き、**単価が未設定のモデルでは実プロバイダの呼び出しを拒否する**（fail closed）。単価は価格改定のたびに人間が更新する。
- 上限判定は、呼び出し前に「最大出力トークン分の費用を見込んで予約」する形にし、同時実行で上限を超えにくくする。
- 評価コマンドの利用記録は、特定ユーザーに属さない「システム」所有の記録として残す（月間上限には合算する）。
- 利用者向けの文言（上限超過など）は日本語の固定文。

### 3. 既存コード・既決の技術選定との矛盾
なし（既存コード・既決の選定がない）。D-003〜D-008、Q-P6/P7/P8/U1 の仮置きと矛盾する要求は見つからない。
ただし Q-P8 の「セッション最長30日目安」は、選定する基盤によっては設定に有料プランが要る（問い4）。

### 4. 規模（1サイクルに収まるか）
**分割を推奨する**（SPEC に書かれた分割案のとおり）。
- 受入基準25件、画面4つ、認証、データ分離の共通テスト部品、LLM共通部分、評価コマンド、PWA雛形と、性質の違うものが同居している。1サイクル（AIエージェントの1回の実装＋検収）に詰めると、不合格時の差し戻しが大きくなる。
- 推奨: SPEC-000a（雛形・認証・分離・削除・テスト基盤・README。AC-1〜12, 22〜25）→ SPEC-000b（LLM共通部分・プロンプト置き場・評価コマンド。AC-13〜21）。000b は 000a の分離の仕組み（利用記録テーブルのRLS）の上に載るので順序は 000a が先。
- 技術選定は分割しても一度にまとめて承認を求める（SPECの記載どおり）。
- AC-3（`.env.example`）は 000a で作り、000b で LLM関連の変数を追記する。

### 5. 非公開性（相手側に原文が漏れる経路）
SPEC-000 の設計上、相手側に原文が漏れる経路は残っていない。
- pair は個人データを読む権限を与えず、AC-10 で確かめている。相手に見える「承認済み伝達文」は別保存（SPEC-004）という分離も整合している。
- LLM利用記録は本文を持たない。ログにも本文を出さない（AC-17, AC-18）。
- 残るのは運用者側の経路で、SPECも未決（Q-P7）としている。architecture.md の E-3 に経路を列挙した（DB管理画面、基盤のログ、LLMプロバイダ側の保持）。
- 補足A（SPEC-001 の前提として）: 相談本文を扱い始める前に、DB基盤・ホスティングのリクエストログ、クエリログに本文が残らないことを確認する受入基準が要る。SPEC-001 のレビュー時に起票するか、SPEC-000 の AC に追加するかは戦略担当が決めてよい（推奨: SPEC-001 側）。
- 補足B: 通知（SPEC-005）は、通知の文面・件名に相談内容を出さない前提を SPEC-005 に書く（Q-P8 の「通知に内容を出さない」）。Web Push は端末の通知センター・ロック画面に表示されるため。

## 戦略担当への問い（要調整）

各問いに、開発担当の提案（既定値）を付けた。実装の都合だけで仕様の意図を変えないため、提案は戦略担当の承認を待つ。

1. **新規登録の重複メールと「メール確認なし」の整合**。SPEC は「メールアドレス確認は公開前の別SPEC」とする一方、第4章は「登録済みのメールアドレスでも他人のアカウントの有無が分かる文言を出さない」を求める。選定案の基盤では、メール確認を使わないと、登録済みメールでの新規登録に「登録済み」と分かる応答が返るのが標準動作になる（アカウント有無が分かる）。メール確認を使えば同一応答にできるが、メール送信基盤が必要で、SPECの範囲外としているものと衝突する。
   - 提案: SPEC-000 の期間（利用者は開発者本人と招待した少数のみ）は、登録時の重複通知は許容し、ログイン時の列挙防止（AC-5）だけを必須とする。登録時の列挙防止とメール確認は公開前SPECで同時に実現する。architecture.md の選定案にこの挙動を書く。
   - 戦略担当または人間が決めること: この限定を許容するか。許容しない場合、メール確認とメール送信（外部サービス＝費用・データ送信を伴う）を SPEC-000 に入れる必要があり、規模が増える。
2. **「1日」「月間」の境界のタイムゾーン**。上限の「1日の呼び出し回数」「月間費用」を、いつ区切るかが未定義。提案: 日本時間（JST）の 0:00 / 月初。
3. **pair の器の最小制約**。AC-10 の分離テストには「同じ pair の2人」を作る必要があるが、pair の制約（メンバー数、1人が持てる連携の数、状態の値）が未定義。SPEC-003 の登録・解除の挙動を縛らない範囲で決める必要がある。提案: メンバーは最大2人、1人が同時に所属できる pair は1つ（DBの制約で表す）、状態は `active` / `ended` のみ。SPEC-003 で変えてよい旨を SPEC に残す。
4. **セッション最長30日（Q-P8）の扱い**。open-questions の推奨は「認証方式の標準の有効期間（最長30日目安）」だが、選定案の基盤（Supabase）では、セッションの有効期限・無操作での失効・強制の単一セッション化は **有料プラン（Pro、月$25）でのみ設定可**（公式ドキュメント、2026-10-07確認）。無料プランの標準では30日という上限を設定できない。
   - 提案: SPEC-000 では「目安」と扱い、有効期間の設定は公開前に有料プランで行う（それまで本人たちの端末のみで試用）。30日を SPEC-000 の必須要件にする場合は、開発中から Pro プランの費用（月$25前後）を承認する必要がある。
5. **LLM利用記録の本人の読み書き権限**。第5章は「相手から見えない」とあるが、本人が自分の利用記録を読めるか・書けるかが未定義。提案: 本人は読み取りも書き込みもしない（利用記録はサーバー側の処理のみが書き、利用者向け画面もない）。分離テスト（AC-9）は「他人から読めない・変更できない」に加え「本人の権限でも書き込めない」を確認する。
