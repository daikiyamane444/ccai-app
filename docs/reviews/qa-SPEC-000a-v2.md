### shim と本物の Supabase の差の評価（architecture.md 11-1）

受入基準の判定を無効にするほどの差は**ない**と判断する。
- 分離の中身（RLS、ロール、権限、ポリシー、トリガー、外部キーの連鎖）は PostgreSQL 自体の機能で、本番と同じマイグレーションの SQL をそのまま適用している。shim の `auth.uid()` は Supabase の定義と同じ（`request.jwt.claim.sub` → `request.jwt.claims` の `sub`）。`service_role` の BYPASSRLS、`public` の既定権限も本物に合わせてあり、マイグレーションが明示的に取り消す書き方なので、本物の既定がもっと緩くても結果は変わらない
- テストの接続がスーパーユーザーである点は、`SET LOCAL ROLE` でロールが切り替わると RLS が通常どおり効くので判定に影響しない（M7 で、切り替えを外すと失敗することを確認）。本番でロールを切り替えられない場合は「エラーになる」側に倒れ、漏れる側には倒れない
- AC-4・5・7 は偽の認証基盤での確認で、アプリ側の論理（文言の統一、cookie、失効後の扱い）の判定としては有効。ただし偽物が本物より甘い点が少なくとも1つある（A-1）ので、偽物の妥当性は 000c で実サービスと突き合わせる必要がある

### 000c に回す確認項目（11-2）の妥当性

項目1〜13は妥当。次の追加を推奨する（宛先: developer。000c の SPEC に入れるなら strategist）。
1. （A-1）**アクセストークンの期限切れ後にログアウトしたとき**、旧 cookie（リフレッシュトークン）で戻れないこと
2. （A-6）アプリ用の DB 接続ロールを、テーブル権限も BYPASSRLS も持たないものにし、`SET LOCAL ROLE` だけで動くこと
3. Supabase の Data API（PostgREST／GraphQL）をアプリは使わないので、無効化するか公開スキーマから外すこと。少なくとも、ログイン利用者が自分のJWTで `/rest/v1/profiles` を直接呼んでも RLS どおり自分の行しか見えないことを確認
4. 本物の Supabase で「管理APIのユーザー削除 → `auth.users` の削除 → `profiles`・`pair_members` の連鎖削除」が権限エラーなく通ること（項目6の具体化）
5. 登録時の「新規登録は本人のメールアドレスのみ」（D-013）が Supabase の設定で効いていること（000c で作らない一覧の「登録メールの制限」と重なるが、D-013 の前提なので確認は必要）

### アカウント削除で「相手が残る pair の行は変更しない」解釈についての所見（開発担当→戦略担当の問い）

非公開性の観点では**問題なし**。理由:
- 削除される利用者の `pair_members` の行は消える。残る `pairs` の行の項目は ID・状態・作成日時だけで、削除された人の個人データを含まない
- 残った相手は RLS により自分の所属行しか読めないため、`pairs` の行が残っても「相手が削除したかどうか」「誰だったか」は分からない（漏れる情報が増えない）
- 他人のデータを一切変えないため、AC-12 の文言にも最も素直に合う

ただし、非公開性以外の面で SPEC-003 で必ず決めるべき点がある（宛先: strategist）。
- 相手は「メンバー1人の active pair」に残り、1人1つの active 制約のため **新しい連携ができなくなる**。SPEC-003 で、削除時に pair を ended にするか、相手にどう知らせるか（知らせ方自体が「相手が退会した」ことを伝えるので、文言を決める必要あり）を決めること
- 後続SPECで、削除された人が相手に送った伝達文など「相手の画面に出ているもの」の扱い（残す／消す）を、プライバシー判断として人間に確認すること（CLAUDE.md「人間へ確認する条件」に該当）

## 人間が画面で確認すべき点
1. （AC-7）ログアウト後にブラウザの戻るボタンで、ホームの内容（表示名を含む）が一瞬でも見えないこと。iPhone Safari（ホーム画面から起動した場合を含む）と PC の Chrome で確認。`ReloadOnBack` は履歴キャッシュから復元された後に再読み込みするため、ちらつきが出ないかも見る
2. （AC-15）幅375pxのスマホ表示で、ログイン・新規登録・ホームに横スクロールがなく、入力時に画面が拡大されず、ボタンと「新規登録はこちら」「ログインはこちら」が押しやすいこと
3. （AC-16）Android Chrome でインストール可能と判定されること、iPhone でホーム画面に追加でき、名前・アイコン・全画面表示になること
4. （AC-17）ログアウト後に機内モードでアプリを開いても、表示名などが表示されないこと
5. （AC-8、000c）HTTPS 環境で cookie に Secure・HttpOnly が付き、開発者ツールのコンソールから `document.cookie` で読めないこと
6. （A-1、000c）ホームを1時間以上開いたままにしてからログアウトし、戻る・再読み込みでホームに入れないこと

評価ケース: 000a は LLM を使わないため、C の応答品質は対象外。後続SPEC用に EV-06（断定の回避）・EV-07（入力負担）を `docs/reviews/eval-cases.md` に追加した。
