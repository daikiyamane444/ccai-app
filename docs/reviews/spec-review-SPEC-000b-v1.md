## 観点別の確認

1. **受入基準のテスト可能性**: おおむね良好。時刻を固定するテスト（AC-5）、並行呼び出しのテスト（AC-6）は、時計と呼び出しを差し替えられる設計にすれば自動テストにできる。
2. **未定義の挙動**: 問い1・2のとおり。ほか下の「実装時の既定値」。
3. **既決・選定案との矛盾**: 既決との矛盾なし。30回・800トークン・30秒は architecture.md の提案と一致。ただし問い1は「完全削除（T-7）」と「費用上限の正確さ（D-007）」が衝突する。
4. **規模**: 受入基準15件。共通部分、利用記録、評価コマンドで1サイクルに収まる。000a の分離・削除の仕組みを使う前提（000a 合格後に実装）。
5. **非公開性**: 利用記録は本文を持たず、本人も読み書きできない設計でよい。アプリのログに本文を出さない確認（AC-9）も妥当。基盤側ログは SPEC-001 へ割り振り済み（総括 2-B）で、000b は本文を扱わないため問題ない。

## 戦略担当への問い（要調整）

1. **ユーザー削除で費用の集計が減ってしまう**。第5章は、利用記録がユーザー単位の全データ削除の対象で、AC-8 でも削除後に消えることを確かめる。しかし月間費用上限と1日の回数上限は、この利用記録を足し合わせて判定する想定。ユーザーが（または開発側が）アカウントを削除すると、その分の費用が月間合計から消え、上限を実質的に回避できる。評価コマンドの「システム」所有の記録は残るので影響は利用者分だけだが、費用の歯止め（D-007）の信頼性に関わる。
   - 提案: 月間の費用・回数の合計は、利用記録とは別の **月次集計**（年月、推定費用の合計、呼び出し回数だけ。ユーザーを特定する項目を持たない）に積み上げ、ユーザー削除の対象外にする。1日の回数はユーザー別の記録から数えてよく、削除で消えてよい（再登録が必要で、登録の抑止は公開準備SPEC）。AC-8 に「削除後も月次集計の合計は変わらない」を足す。
   - 戦略担当または人間が決めること: 個人に紐づかない集計だけを削除後も残してよいか（データ保存に関わるため、人間への確認が望ましい）。許容しない場合は、月間上限の判定を削除済み分も含めて行う別の方法（たとえば削除時に費用だけを匿名のまま残す）を戦略担当が決める必要がある。
2. **「設定不足」の結果値と、1日の回数に数える範囲**。第7章は上限未設定・単価未設定の場合に「上限超過（または設定不足）」を利用記録に残すとするが、第5章の結果の値は「成功／失敗／上限超過／タイムアウト」の4つだけ。また1日の回数上限に、拒否した呼び出し（上限超過、設定不足）を数えるかが未定義。
   - 提案: 結果の値に「設定不足」を追加する。1日の回数には、実際にプロバイダへ送った呼び出し（成功・失敗・タイムアウト。再試行は合わせて1回）だけを数え、プロバイダを呼ばなかった拒否は数えない。

## 実装時の既定値（開発側で置く。README または architecture.md に記録する）

- 上限の予約（AC-6）は、入力側の見込み（文字数からの保守的な見積もり。日本語は1文字を最大1トークンとみなす）に、最大出力トークン分を足した費用で行う。第6章の文言は出力分だけだが、入力分を含めないと確定後に超えるため、入力の見込みも含める。AC-6 の許容（上限を超えても1回分の見込み費用未満）の範囲でテストする。
- タイムアウトやプロバイダのエラーで実際のトークン数が分からない場合は、予約した見込み費用をそのまま「推定費用」として確定する（過小計上を避ける）。
- 「システム」所有の記録は、実在のアカウントを指さない固定の所有者値で持つ（認証基盤のアカウントに連動して消えない形）。どの利用者の権限からも読めない。
- 評価コマンドは1日の回数上限の対象にしない（月間費用には合算する）。評価結果のファイルには、APIキーなどの設定値を書かない。
- AC-6 の文言は「確定後の合計が上限を超えない」でも実装は同じ。意味を明確にするなら次の改訂で簡潔にしてよい（軽微）。
