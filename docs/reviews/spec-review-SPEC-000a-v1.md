## 判定: 実装可
（意味: 技術選定 Q-H10 が人間に承認され decisions.md に記録されれば、実装モードに入れる）

前回の問い1〜5のうち000aに関わる1・3・4への回答はいずれも技術的に実現でき、受入基準もテストで確かめられる形になっている。

## 観点別の確認

1. **受入基準のテスト可能性**: 良好。AC-8 が「スクリプトからトークンを読めない」に一般化され、満たせない場合の止め方（実装の最初に確認、戦略担当へ戻す）が書かれている。AC-9 に匿名権限、AC-13 に pair 制約、AC-14 に特権の限定が加わり、データ層を直接呼ぶテストにできる（選定案ならローカルDBに利用者・匿名の権限で接続して検証）。
2. **未定義の挙動**: 重大なものはない。下の「実装時の既定値」は開発側で置いてよい範囲。
3. **既決・選定案との矛盾**: なし。Q-P8（上限設定なし）、Q-P9（登録時の重複通知を許容する仮決定）、Q-U1 と整合する。
4. **規模**: 受入基準18件。PWA雛形、認証、データ分離、削除、テスト基盤と盛りだくさんだが、LLMを外したため1サイクルに収まる範囲と判断する。ただし AC-8（HttpOnly）が成立しない場合は戻す前提。
5. **非公開性**: 相手側に原文が漏れる経路は残っていない。pair は個人データの読み取り権限を与えない（AC-10）、登録済みメールでの登録でも既存アカウントの情報は出ない（第4章・第7章）。

## 実装時の既定値（開発側で置く。README または architecture.md に記録する）

- パスワードの最小文字数・形式の検証: 認証基盤の標準に従い、8文字以上を既定にする（基盤の標準値が6の場合は上書き）。仕様の意図は変えない。
- ローカルでメール確認を使わない設定にする（Q-P9 仮決定の前提）。
- pair のテーブルの読み取り: メンバー本人だけが自分の pair の行を読める。非メンバーと匿名は読めない。書き込みはテスト用の手段のみ（特権の部品経由）。
- 全データ削除は、認証基盤上のアカウント本体の削除を含める（プロフィール・pair の所属も含む）。
- Service Worker は、ログイン後の画面とAPI応答をキャッシュしない設計を既定にする（AC-17。基本は「キャッシュしない」で実装する）。

## 軽微な指摘（判定に影響しない。戦略担当が次の改訂で拾ってよい）

- 第7章「登録済みメールでの新規登録」の振る舞い（既存アカウントにログインされない、情報が出ない）には対応する受入基準がない。AC-4 に「登録済みメールで登録してもセッションが発行されず、既存アカウントの情報が表示されない」を足すとテストで確かめられる。実装側では追加しても問題なく、テストは書く。
- AC-3 の「キーらしき文字列のgrep」は、ローカル用の公開既定値（選定案のローカル基盤が配る固定のデモ用キー）に反応する可能性がある。仕様に「ローカル開発用に公開されている既定値は可、その旨を注記」とあるので、実装側はその注記を付ける。
