## 問い（000b の実装は止めない）

### 問い1（人間へ）: 実LLMの評価を、どこで動かすか
評価コマンドはどこでも動く作りにした。必要な秘密は、プランの長期トークン（`CLAUDE_CODE_OAUTH_TOKEN`）と DB の接続情報（月次集計に記録するため）。
どちらの案でも、トークンを作るために人間の PC で1回だけターミナル操作（Claude Code を入れて `claude setup-token`）が要る（ブラウザだけで作る方法は見つからなかった）。

| 案 | 人間の作業 | 結果の受け取り | 注意 |
| --- | --- | --- | --- |
| (a) 人間の PC のターミナルで実行 | Node.js の導入、リポジトリの取得、`npm ci`、`.env.local` の設定、`npm run eval -- --prompt <名前> --real` | 結果ファイルが PC にできる。人間が問い合わせ担当に渡す（中身は架空の評価ケースと応答なので、渡してよい） | 非エンジニアには作業が多い |
| (b) GitHub Actions の手動ジョブ（推奨） | トークンを GitHub の Actions secrets に1つ追加（DB の秘密は 000c で設定済み） | ジョブが結果ファイルを、評価結果専用のブランチ（例: `eval-runs`）にコミットする。AI はそのブランチを git で読む（ログ本体・成果物の取得は作業環境から拒否されるため） | ワークフローが専用ブランチへ書き込む（D-015 の「push は問い合わせ担当だけ・main だけ」の例外になる）ので人間の承認が要る。プランのトークンを GitHub に置く（Anthropic の公式 GitHub Actions 連携も同じ置き方をする） |

推奨は (b)。決まったら、ワークフロー（評価ジョブ）と手順書を追加する（30分程度の作業）。

### 問い2（戦略担当・人間へ。SPEC-001 より前に必須）: プラン方式を使ってよい範囲
Claude Code の「Legal and compliance」（https://code.claude.com/docs/en/legal-and-compliance 、2026-10-09 確認）:
- 「OAuth 認証（プランのログイン）は、プランの購入者が Claude Code などの Anthropic のアプリを通常どおり使うためのもの」
- 「Agent SDK を使う製品・サービスを作る開発者は、APIキーの認証を使うべき。第三者の開発者が、自分のアプリで Claude.ai のログインを提供したり、利用者の代わりにプランの認証で要求を送ったりすることは許可しない」
- 「Pro・Max の利用上限は、Claude Code と Agent SDK の通常の個人利用を前提にしている」

解釈（開発担当。法的な判断ではない）:
- 000b の範囲（人間本人が、自分のプランで評価ケースを流す）は「個人の通常の利用」に当たると考えられ、D-010・D-014 と両立する。
- **SPEC-001 以降で、公開したアプリ（Vercel）の相談機能がプランの認証で LLM を呼ぶことは、利用者が人間本人だけでも「製品からプランの認証で要求を送る」形になり、規約に反するおそれが高い。パートナーが使えば明確に「利用者の代わり」に当たる。**
- したがって D-010 の「リリースまではプラン方式」は、**評価コマンドに限る**と読み替え、アプリの機能（SPEC-001）は最初から APIキー方式（費用上限を人間が承認）にするのが安全と考える。D-010 の変更になるので人間の決定が要る。

## 実装時の既定（このレビューで決めたもの）
- 実行方式の切替え `LLM_MODE`（mock 既定 / plan）。プラン方式の認証情報は環境変数 `CLAUDE_CODE_OAUTH_TOKEN` だけ（開発機のログイン情報は使わない。SDK の設定フォルダを一時フォルダにして、手元の設定・記録に触れないため）
- 単価・為替・上限は環境変数。値は空で配り、人間が評価の前に入れる（.env.example）
- 存在しないプロンプト名は、利用記録に「設定不足」（種類 `unknown_prompt`）として残す
- 呼び出し中の記録は一時的に `pending`（同時に来ても1日の回数・月間を超えないため）。完了時に5種類のどれかにする
