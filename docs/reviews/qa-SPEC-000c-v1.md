**S-1（軽微。宛先: strategist）登録の許可リストと、D-011 の「登録済み」応答の組み合わせ**
- 一覧外のアドレスは 403「受け付けていません」、本人のアドレスは登録後なら 409「登録済み」になる。公開URLを知っている人は、候補のアドレスを入れて応答の違いを見ることで「どれが本人のアドレスか」を確かめられる。拒否の応答そのもの（AC-5）は満たしているが、登録窓口全体としては一覧の中身を確かめる手段になる。これは D-011 で公開前まで許容した「登録済みと分かる」動作の延長で、新しい漏れではない
- また、デプロイ（手順9）から本人の登録（手順11）までの間は、本人のアドレスを知る人が先に登録できてしまう（メール確認がないため）
- 対応案（手順書の追記で足りる）: 手順9のあとすぐに手順11-1で本人が登録する、と明記する。本人の登録が終わったら `SIGNUP_ALLOWED_EMAILS` を空にして Redeploy すれば、登録は完全に閉じ、409 による確認もできなくなる（fail closed のため）。この運用を採るかを strategist が決める

### `.github/workflows/` を app/ の外に置いた点（D-015 の範囲か）
**範囲内と判断する。** GitHub Actions はリポジトリ最上位の `.github/workflows/` にある定義しか読まないため、置き場所は技術的に決まっている。D-015 は「GitHub Actions で本物の Supabase に結合テストを流すこと（手動起動、SPEC-000c の条件どおり）」を許可しており、この定義はその条件（`workflow_dispatch` のみ、`permissions: contents: read`、secrets は env 経由のみ、postgres の管理者パスワードを使わない、`concurrency` で同時実行なし、`pull_request`・`push`・`schedule` なし）を満たす。静的テスト（`static-checks.test.ts`）がこれらを毎回確かめる。CLAUDE.md の担当表では developer の成果物は「`app/` 以下」だが、このファイルは SPEC-000c 第2章 6・2-B で明示された成果物なので、範囲外の変更には当たらない。人間への報告で「リポジトリ最上位に `.github/` が1つ増える」ことを一言伝えるとよい。
外部から secrets が使われる経路: `pull_request`／`pull_request_target`／`workflow_run` がないため、フォークや外部のPRから起動されることはない。起動できるのは書き込み権限を持つ人（本人と、D-015 の範囲の AI）だけ。
