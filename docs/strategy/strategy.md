# 戦略（v5）

> 管理者: strategist。根拠は `docs/sources/` の要件整理（以下「整理」）。
> 「推奨案」は戦略担当の提案で、人間の決定ではない。決定は `docs/decisions.md` を正とする。

## 1. 目的

気持ちをうまく言葉にできない二人が、直接言うとぶつかることを、適した形・適したタイミングで伝え合えるようにする。（整理 3.4、4.1、4.4）

## 2. 解く課題（会話で語られた見方。効果は未検証）

- 「もういい」「察して」で対話が止まり、関係が壊れる。
- 直接言うと押し付け・非難に受け取られる。
- 話したいタイミングが二人でずれる（休日に話したい／休みたい）。
- 言語化が苦手な人は、チャットの自由記述だけでは使えない。

## 3. 中核となる体験（構想）

1. **個別の相談窓口（裏垢のような場所）**：各自が自分のスマホで、不満・要望・不安を書く。相手には直接見えない。（整理 3.5）
2. **言語化の支援（通訳）**：本人から言葉を引き出し、要望として整理する。（整理 4.1）
3. **伝え直し**：要望の中身を保ちつつ、押し付けにならない表現で相手へ届ける。（整理 3.5、3.6）
4. **時機の調整**：相手の状況に合わせて伝える。単純な時間差・通知でも価値がある。（整理 3.9、4.4）
5. **対等さの保持**：一方の主張が偏ったら、本人へ相手の状況を問い返す。（整理 3.6）

## 4. 設計原則

非公開性最優先／対等さ／推測と事実の区別／入力負担を小さく／効果を断定しない／危険な兆候は専門窓口へ。
（詳細は `.claude/agents/strategist.md` の「判断の原則」）

## 5. 初回開発範囲（MVP）— 決定済み（D-003〜D-007）

**対象利用者**（D-003）：成人の交際中カップル・夫婦（同性カップルを含む）。一人でも相談でき、相手への伝達は二人の連携後。
**形式**（D-006）：スマホ対応のWebアプリ（PWA）。公開先は検収後に決める。
**伝達**（D-005）：送信前の本人確認を必須とし、自動送信はしない。

### 実装の順序（推奨案・各SPECのサイクルで確定）
1. SPEC-000 技術基盤（技術選定は D-009・D-010 で承認済み）— SPEC-000a 雛形・認証・分離・削除・テスト（検収合格）→ SPEC-000c 個人用公開（D-013）と SPEC-000b LLM共通部分・プロンプト・評価コマンド。000c と 000b は互いに依存しないため、000c で人間の作業を待つ間に 000b を進めてよい
2. SPEC-001 個別相談チャット＋安全経路
3. SPEC-002 言語化支援
4. SPEC-003 アカウント連携（招待コード、解除）
5. SPEC-004 伝え直し＋送信前確認
6. SPEC-005 時間差伝達・通知
7. SPEC-006 簡易問診

理由：一人用の相談だけで先に試せ、中核の伝え直しの品質を早く確かめられる。安全経路は最初の相談機能と同時に入れる。
SPEC-004 合格後、開発者自身が1〜2週間使い、第7章の前提を確かめる。

### MVPの機能（D-004）

**含める候補**
- 二人のアカウント連携（招待コード方式）
- 個別チャットでの相談と言語化支援
- 相手への伝え直し：**送信前に本人が伝達文を確認・承認する**（自動送信はしない）
- 伝達タイミング：本人指定の時間差＋相手が好きなときに開く通知（AIによる時機推定は後回し）
- 簡易な初回問診（数問・スキップ可）
- 安全経路（危険な兆候で専門窓口案内）

**後回し**：外部データ連携（睡眠・GPS・LINE・X等）、MBTI・四柱推命、日々のスライダーログ、けんかの仲裁、主張量の自動判定

**範囲外（別構想）**：独身者の相談・マッチング、親子・学校・職場向け、企業向け伝達ツール、売却・事業計画

推奨理由：中核体験（1〜4）を最小の入力負担で検証でき、非公開性のリスクを「送信前確認」で抑えられる。外部連携は同意・技術条件が未確定（整理 5.5）。

## 6. アプリ内エージェント構成（構想・未決 Q-S9）

一つの相談窓口（受付）が内容と関係性の情報を見て専門の処理へ振り分ける。（整理 4.3）
MVPでの候補: 受付 → {言語化支援, 伝え直し, 問い返し（対等さ）, 安全対応}。
開発体制のAI（このハーネス）とは別物として設計する。

## 7. 未検証の前提（検証方法を今後決める）

- 関係を良くしたい二人なら入力の手間を受け入れる（整理 3.4）
- AIからの伝え直しのほうが受け止めやすい（整理 4.5、4.7）
- 時間差で伝えることに価値がある（整理 4.4）

## 8. 技術基盤の方針（SPEC-000）

技術構成は人間が承認済み（D-009: Next.js＋Supabase 東京／D-010: Claude）。プライバシーの前提は D-011、削除後の月次集計は D-012。戦略として土台に求めるのは次の4点（推奨案）。

1. **非公開性をデータ層で守る**：個人データはすべて所有者1人に属し、二人の連携は相手の個人データを読む権限を与えない。相手に見えるのは本人が承認した伝達文（SPEC-004）だけで、個人データとは別に保存する。画面やAPIの注意だけに頼らず、データ層で強制し、分離テストを全SPECで使い回す。
2. **相談本文を外に出さない**：ログ・エラー記録・利用記録に本文を残さない。LLMプロバイダは入力を学習に使わないことを確認できるものに限る。保存地域・運用者の閲覧可否・保存期間は人間が決める（Q-P4・Q-P6・Q-P7）。
3. **費用を先に縛る**：LLM呼び出しは共通部分1か所を通し、回数・費用の上限を設定がなければ止まる側（fail closed）で持つ（D-007）。月間の合計は個人に紐づかない月次集計で数え、削除で減らない（D-012）。
4. **品質の確かめ方を最初に用意する**：自動テストはモックで、実LLMの応答品質は評価コマンドで手動確認する（D-008）。

土台は利用者向けの機能を持たないため、SPEC-000 だけでは第7章の前提は検証できない。開発担当のレビューを受け、SPEC-000a（雛形・認証・分離・削除・テスト）と SPEC-000b（LLM共通部分・プロンプト・評価コマンド）に分けた。000a が先。

**LLMの実行方式（D-010）**
- リリースまでは、人間が契約中の Claude プランの Agent SDK クレジット枠の中で、Agent SDK 経由で呼ぶ（プラン方式）。追加課金は有効にしないので、枠を使い切ったら止まる。これが外側の歯止めになる。アプリ側の金額上限は「請求額」ではなく「消費の目安」として持つ。
- Agent SDK はエージェント（ツールを使える）なので、アプリでは文章生成だけに絞る。ツールはすべて無効、プロジェクトの設定ファイルは読まない、1往復、会話記録を手元に残さない。利用者の入力からサーバー上のファイル・秘密情報に届く経路をなくすため（SPEC-000b）。
- 個人向けプランでは、API の「既定で学習に使わない」がそのまま当てはまるとは限らない。そのため実LLM評価の前に、データ利用設定と適用規約を確認する（Q-H11）。確認できるまで、実利用者の本文は送らない。
- 他人（パートナー）が使う段階とリリース時は、APIキー（従量課金）方式への切替えが必要になり得る（Q-H12）。切替えはアダプタ1つの追加で済む設計にする。切替えと費用上限は人間が改めて承認する（D-010）。

**個人用公開（D-013、SPEC-000c）**
- 当面の検証は本人だけが行う。iPhone と PC から HTTPS の個人用URLで使う。
- 新規登録は、サーバー側の許可一覧で本人のメールアドレスに限る。一覧がなければ登録できない（fail closed）。
- 検索エンジンには載せない。
- AI は Supabase・Vercel に直接つながらない。そのため、次の3つの経路を組み合わせる。
  - 人間がブラウザで行う設定（手順書 `docs/runbooks/deploy-personal.md`）
  - GitHub 非公開リポジトリ経由の取り込み
  - GitHub Actions による本物での結合テスト（手動起動）
- 後の2つは、ハーネスの「push しない」規則に当たるので人間の承認が要る（Q-H14）。
- 費用は0円が前提。カード登録や有料機能が必要になったら止めて人間に聞く。
- 000c の目的は、000a の非公開性の仕組みが実サービスの上でも成り立つことを、相談本文を扱う前に確かめることにある。確かめる内容は、期限切れトークンでのログアウト、最小権限のDB接続ロール、Data API の無効化、削除の連鎖。

後続SPECへの申し送り（推奨案）:
- **SPEC-001**: 相談本文を扱い始める前提として、DB・認証基盤・ホスティングの基盤側ログ（リクエスト・クエリ・エラー記録・管理画面の記録）に本文が残らないことを受入基準に入れる。アプリロックの要否（Q-P8 の残り。D-011 で「SPEC-001 前に決める」と決定）を人間に確認する。Q-H11（プランの学習利用設定）が確認済みであることを前提にする。
- **SPEC-001 の前**: 結合テストをテスト専用プロジェクトに分けるか決める（Q-H13）。
- **SPEC-003**: アカウント削除後に相手が残る pair・伝達済みの文の扱い（Q-P10。(2)(3) は人間に確認）。テスト専用の pair 作成関数の置き場所（QA A-7）を直す。
- **公開準備SPEC（追加）**: `/api/auth/refresh` を GET から状態を変えない形へ見直す（QA A-9）。
- **SPEC-003 着手前**: Q-H12（二人での試用がプラン利用の範囲に収まるか）を人間に確認する。収まらなければ、APIキー方式のアダプタを追加するSPECを先に入れる。
- **SPEC-005**: 通知の文面・件名に相談内容を出さない（ロック画面に表示されるため。Q-P8）。
- **公開準備SPEC（公開前・名称仮）**: メール確認、パスワード再設定、新規登録時にアカウントの有無を明かさない動作（Q-P9）、セッション有効期間の上限（Q-P8）、利用規約・プライバシーポリシー、公開先の基盤ログの確認。
