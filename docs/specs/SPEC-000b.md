# SPEC-000b: 技術基盤 — LLM共通部分・プロンプト・評価コマンド（v1）

- 状態: レビュー中（技術選定 Q-H10 と費用上限 D-007 の具体額の人間承認が `docs/decisions.md` に記録され、かつ SPEC-000a が検収合格するまで実装しない）
- 関連: 総括 [SPEC-000](SPEC-000.md) v2、[SPEC-000a](SPEC-000a.md)、戦略 第8章、決定 D-007 / D-008、未決 Q-H10 / Q-P4 / Q-P6 / Q-P7
- 由来: SPEC-000 v1 の範囲 6〜8、AC-9（利用記録の部分）・AC-12（同）・AC-13〜AC-21 を分割。レビューの問い2・5 と軽微点（単価、予約、システム所有の記録、日本語固定文）を反映

## 1. 目的

アプリ内のLLM呼び出しを1か所に集め、APIキーの保護、費用・回数の上限、本文をログに出さないことを、後続SPECが意識しなくても守られるようにする。あわせて、実LLMでの応答品質を手動で確かめる評価コマンドの枠を用意する。

## 2. 範囲

- 含む:
  1. LLM呼び出しの共通部分（プロバイダ差し替え、モック、APIキーはサーバー側のみ、上限、タイムアウト、利用記録）
  2. LLM利用記録（000a の「個人データを追加する手順」に従って追加する）
  3. `app/prompts/` の置き場（形式の説明とサンプル1件）
  4. 評価コマンドの枠（試走と実LLM。結果を `docs/reviews/eval-runs/` に保存）
  5. `.env.example` と `app/README.md` への LLM 関連の追記
- 含まない: 利用者向けのAI機能（SPEC-001以降）、利用者が自分の利用状況を見る画面、基盤側ログの確認（SPEC-001。総括 第2-B章）、総括 SPEC-000 第2章「含まない」の各項目

## 3. 利用者の流れ

利用者向けの流れはない。開発者向け:
1. 自動テストはモックで動く（APIキー不要）。
2. 評価コマンドをまず試走（モック）で動かす。
3. 人間が承認したAPIキーと費用上限を `.env` に設定し、実LLMで評価ケースを流す。結果ファイルを人間と品質担当が読む。

## 4. 画面・入出力

画面なし。

**評価コマンド**（例：`npm run eval -- --prompt <名前>`。名前は技術選定に合わせる）
- 入力: プロンプト名、ケースIDでの絞り込み（任意）、試走か実LLMか。
- 評価ケースは `docs/reviews/eval-cases.md` の表（EV-xx）から読む。
- 実LLMの場合、開始前に件数と推定最大費用を表示する。
- 出力: `docs/reviews/eval-runs/YYYYMMDD-HHMM-<プロンプト名>.md`（日本時間）。記載項目：実行日時、プロバイダ・モデル名、プロンプト名と版、試走か実LLMか、ケースごとの入力・応答・トークン数・推定費用、合計費用。評価ケースは架空の入力なので、ここには入力・応答を書いてよい（実利用者のデータは使わない）。

## 5. データ

| データ | 主な項目 | 相手から見えるか | 本人の権限 | 保存期間 | 区分 |
| --- | --- | --- | --- | --- | --- |
| LLM利用記録 | 所有者（ユーザー、または評価コマンド用の「システム」）、日時、プロンプト名、プロバイダ・モデル名、入力/出力トークン数、推定費用、結果（成功／失敗／上限超過／タイムアウト）。**入力文・応答文は保存しない** | 見えない | **読み取りも書き込みもできない**（サーバー側の処理だけが書く。問い5への回答・採用） | 削除するまで（仮置き Q-P4） | システム記録 |

- 000a の「個人データを追加する手順」に従う。分離の仕組みに登録し、分離テストの共通部品でテストし、ユーザー単位の全データ削除の対象に加える。
- 「システム」所有の記録（評価コマンドの実行分）は、どの利用者からも読めない。ユーザー削除の対象外だが、月間上限には合算する。
- 問い5の採用理由: 利用者向け画面がなく、本人が書けると上限の回避（記録の改ざん）につながるため。将来、本人に残り回数を見せる必要が出たら、そのSPECで読み取りだけを追加する。

## 6. AIの振る舞い

このSPECでは利用者向けのAI機能を作らない。作るのは呼び出しの共通部分だけ。

**共通部分の決まり**
- アプリ内のすべてのLLM呼び出しは、この共通部分1か所を通す。プロバイダのSDK・APIを直接呼ぶコードは共通部分の中（プロバイダごとの差し替え部品）だけに置く。
- プロバイダは設定（環境変数）で切り替える。少なくとも「モック」と、承認された実プロバイダ1つを用意する。**自動テスト実行時は設定にかかわらずモックを使い**、外部に通信しない。ローカル起動でもAPIキーがなければモックで動く。
- モックはプロンプト名ごとに固定の応答を返す。テストから応答・失敗・遅延を指定できる。
- APIキーはサーバー側の環境変数だけで扱い、ブラウザに届くコード・応答に含めない。

**上限**（値は環境変数。**未設定・不正な値なら実プロバイダへの呼び出しをすべて拒否する**）
- 1ユーザーあたり1日の呼び出し回数上限。仮置きの初期値は **30回**（architecture.md の提案に合わせる。承認された値に従う）。
- アプリ全体の月間推定費用上限（円）。具体額は技術選定と同時に人間が承認する（D-007）。評価コマンドの実行分も含める。
- 1回あたりの最大出力トークン数（仮置き 800。承認された値に従う）。
- **日・月の区切りは日本時間（JST）の 0:00 と毎月1日 0:00**（問い2への回答・採用）。
- **モデル別の単価**（入力・出力それぞれ）と、費用を円にするための為替レートは設定値で持つ。**単価が設定されていないモデルは実プロバイダで呼ばない**。単価は価格改定時に人間が更新する。
- 上限の判定は、呼び出し前に「最大出力トークン分を見込んだ費用」を予約して行い、同時に呼ばれても上限を超えにくくする。呼び出し後に実際のトークン数で記録を確定する。
- 上限を超えたら、プロバイダを呼ばずに決まったエラーを返す。利用者向け文言は日本語の固定文（例：「今日はAIの利用上限に達しました。明日またお試しください」）。

**その他**
- タイムアウト（仮置き: 30秒）。一時的な失敗は1回だけ再試行してよい。
- 呼び出しごとに第5章の「LLM利用記録」を残す。**相談本文（入力・応答）は、アプリのログ、エラーログ、利用記録のどこにも出さない**。エラー内容を記録する場合も本文を含まない形（エラーの種類・コード）にする。
- プロンプトはコードに埋め込まず `app/prompts/` のファイルから名前で読み込む。

**`app/prompts/` の置き場**
- `app/prompts/README.md`：1ファイル1プロンプト、ファイル先頭に「対応SPEC番号・目的・版・最終更新日」を書く形式の説明。
- サンプル1件（例：`_sample.md`、SPEC-000b、共通部分と評価コマンドの動作確認用。受け取った文をそのまま短く言い換えるだけ）。
- 良い例：プロンプトに SPEC 番号と版があり、変更履歴を追える。悪い例：プロンプト文がコード内の文字列に散らばっている。

## 7. 例外・エラー

| 状況 | 振る舞い |
| --- | --- |
| APIキーなし | ローカル起動・テストはモックで動く。実プロバイダ指定時は呼び出しを拒否し、設定不足を示すエラー（キーの値は表示しない） |
| 上限超過・上限未設定・単価未設定 | プロバイダを呼ばずに決まったエラー。利用記録に「上限超過」（または設定不足）を残す |
| タイムアウト・プロバイダのエラー（プロバイダ側の利用上限による拒否を含む） | 1回まで再試行後、決まったエラー。本文をログに出さない |
| 存在しないプロンプト名 | 決まったエラー（開発者向け）。プロバイダを呼ばない |
| 評価コマンド: APIキーなしで実LLM | 何も送信せずにエラーで止まる |
| 評価コマンド: 推定最大費用が月間上限の残りを超える | 実行しない |
| 評価コマンド: eval-cases.md の表が読めない・該当IDなし | 何も送信せずにエラーで止まる |

## 8. 受入基準（品質担当が判定する）

- [ ] AC-1（旧AC-13）: プロバイダのSDK・APIを直接呼ぶコードが共通部分の差し替え部品の中にしかない。（確かめ方: SDK名・APIのURLを `app/` 全体でgrep）
- [ ] AC-2（旧AC-14）: 実プロバイダが設定されていても、自動テスト実行時はモックが使われ外部に通信しない。モックはプロンプト名ごとの固定応答を返す。（確かめ方: 自動テスト。外部通信を遮断した状態でも通る）
- [ ] AC-3（旧AC-15）: ダミーのAPIキー（目印になる文字列）を設定してブラウザ向けのビルドを作ると、成果物にその値もAPIキーの環境変数名も含まれない。（確かめ方: 自動テストまたはスクリプトでビルド成果物をgrep）
- [ ] AC-4（旧AC-16）: 1日の回数上限・月間費用上限を小さく設定すると、上限に達した後の呼び出しはプロバイダ（モック）を呼ばずに決まったエラーを返す。上限の設定を消した・不正な値にした場合、および単価が未設定のモデルを指定した場合も、実プロバイダへの呼び出しはすべて拒否される。（確かめ方: 自動テスト）
- [ ] AC-5（新）: 日の境界は日本時間0:00、月の境界は日本時間の毎月1日0:00で切り替わる（例：日本時間23:59に上限に達した利用者が、0:00以降は再び呼べる）。（確かめ方: 時刻を固定した自動テスト）
- [ ] AC-6（新）: 月間上限の残りが1回分の見込み費用に満たないとき、同時に複数の呼び出しが来ても、確定後の合計が上限を1回分の見込み費用以上に超えない。（確かめ方: 自動テスト）
- [ ] AC-7（旧AC-17）: 呼び出しごとに第5章の項目で利用記録が1件残り、入力・応答の本文は含まれない。（確かめ方: 自動テスト）
- [ ] AC-8（旧AC-9・AC-10・AC-12 の利用記録部分）: 000a の分離テストの共通部品を使い、ユーザーAの利用記録をユーザーB・Aの連携相手・匿名の権限から読めず変更・削除できないこと、**A本人の権限でも読み書きできない**ことを確かめる。全データ削除でAの利用記録が消え、他ユーザーと「システム」の記録は変わらない。（確かめ方: 自動テスト。共通部品の追加が数行で済んでいることもコードで確認）
- [ ] AC-9（旧AC-18）: 目印の文字列を含む入力で、成功・プロバイダのエラー・タイムアウト・上限超過の4経路の呼び出しを行い、テスト中に出力されたアプリのログ（標準出力・エラー出力を含む）と利用記録のどこにも目印が現れない。（確かめ方: 自動テスト）
- [ ] AC-10（旧AC-19）: プロンプトは `app/prompts/` のファイルから名前で読み込まれ、存在しない名前ではプロバイダを呼ばずにエラーになる。`app/prompts/README.md` とサンプル1件があり、サンプルの先頭にSPEC番号・目的・版がある。（確かめ方: 自動テストとファイル確認）
- [ ] AC-11（旧AC-20）: 評価コマンドを試走モードで実行すると、APIキーなし・外部通信なしで `docs/reviews/eval-cases.md` の評価ケースを読み、第4章の項目を含む結果ファイルが `docs/reviews/eval-runs/YYYYMMDD-HHMM-<プロンプト名>.md` に保存される。ケースIDでの絞り込みができる。（確かめ方: 自動テスト、または品質担当が実行してファイル確認）
- [ ] AC-12（旧AC-21）: 実LLMモードでAPIキーがない場合は何も送信せずにエラーで止まる。推定最大費用が月間上限の残りを超える場合は実行しない。開始前に件数と推定最大費用を表示する。評価の実行分は「システム」所有の利用記録に残り、月間上限に合算される。（確かめ方: 自動テスト。実LLMでの実行は人間が承認後に手動で1回行い、結果ファイルを品質担当が確認する。未実施なら「未検証」とする）
- [ ] AC-13（旧AC-3 の追記分）: `.env.example` に LLM 関連の環境変数（プロバイダ切替、APIキーの変数名、各上限、モデル別単価、為替レート、タイムアウト）が説明つきで追記され、実際の値を含まない。`app/README.md` に評価コマンドの使い方がある。（確かめ方: ファイル確認）
- [ ] AC-14: `.env` なし・APIキーなしで、000a と 000b の全自動テストが1コマンドで失敗0件で終わる。（確かめ方: 品質担当が実行）
- [ ] AC-15: 利用者向けのAI機能、利用状況の画面、承認されていない外部サービスが組み込まれていない。（確かめ方: コードと依存関係の確認）
