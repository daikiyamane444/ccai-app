- 状態: レビュー中（調整2往復目の改訂。技術構成は D-009、LLMは D-010 で承認済み。SPEC-000a の検収合格後に実装する）

## 1. 目的

アプリ内のLLM呼び出しを1か所に集める。そのうえで、認証情報の保護、使いすぎの歯止め、本文をログに出さないことを、後続SPECが意識しなくても守られるようにする。あわせて、実LLMでの応答品質を手動で確かめる評価コマンドの枠を用意する。

## 2. 範囲

**LLMの実行方式（D-010）**
- アプリで使うモデルは Claude。主案は Sonnet 5.5、代替は Haiku 4.5 で、評価ケースで比べて確定する。
- リリースまでは、人間が契約中の Claude プランに付属する Agent SDK のクレジット枠の中で、Claude Agent SDK 経由で呼ぶ（以下「プラン方式」）。**追加課金（利用クレジット）は有効にしない**前提とする。クレジットを使い切ったら、呼び出しは止まってよい。
- リリース時（または他人に使わせる段階。Q-H12）は APIキー（従量課金）に切り替える。切替えと費用上限は、その時点で人間が改めて承認する。

- 含む:
  1. LLM呼び出しの共通部分
     - 差し替え部品（アダプタ）の共通の形
     - **プラン方式のアダプタ**と**モック**
     - 認証情報はサーバー側だけで扱う
     - 回数・消費の上限、タイムアウト、利用記録
  2. LLM利用記録（000a の「個人データを追加する手順」に従って追加する）
  3. 月次集計（個人を特定する項目を持たない。削除の対象外。D-012）
  4. `app/prompts/` の置き場（形式の説明とサンプル1件）
  5. 評価コマンドの枠（試走と実LLM。結果を `docs/reviews/eval-runs/` に保存）
  6. `.env.example` と `app/README.md` への LLM 関連の追記
- 含まない:
  - **APIキー方式のアダプタ**。リリース準備時の別SPECで、人間の承認（D-010）を得てから作る。
    - 理由: 承認前の課金経路をコードに置かない。実プロバイダで確かめる手段もなく、検収できない。
    - 代わりに、アダプタの共通の形を文書化する。追加がアダプタ1つと設定で済むことは、モックとプラン方式の2つが同じ形で差し替えられることで確かめる（AC-1）。
  - 利用者向けのAI機能（SPEC-001以降）と、利用者が自分の利用状況を見る画面
  - 基盤側ログの確認（SPEC-001。総括 第2-B章）
  - 総括 SPEC-000 第2章「含まない」の各項目

## 3. 利用者の流れ

利用者向けの流れはない。開発者向けの流れは次のとおり。
1. 自動テストはモックで動く。認証情報は要らない。
2. 評価コマンドを、まず試走（モック）で動かす。
3. 人間が Q-H11 を確認する（プランの種類、追加課金が無効であること、プランのデータ利用設定で学習への利用がオフであること、消費の目安の上限値）。そのうえで、プラン方式の認証情報を開発機のサーバー側環境に設定し、実LLMで評価ケースを流す。
4. 結果ファイルを人間と品質担当が読み、主案と代替のモデルを比べる（D-010）。

## 4. 画面・入出力

画面なし。

**評価コマンド**（例：`npm run eval -- --prompt <名前>`）
- 入力: プロンプト名、モデル（主案／代替）、ケースIDでの絞り込み（任意）、試走か実LLMか。
- 評価ケースは `docs/reviews/eval-cases.md` の表（EV-xx）から読む。
- 実LLMの場合、開始前に件数と推定最大消費（後述の「推定費用」）を表示する。
- 出力ファイル: `docs/reviews/eval-runs/YYYYMMDD-HHMM-<プロンプト名>.md`（日本時間）。
  - 記載項目: 実行日時、実行方式（プラン方式／モック）、モデル名、プロンプト名と版、試走か実LLMか、ケースごとの入力・応答・トークン数・推定費用、合計。
  - 評価ケースは架空の入力なので、入力・応答を書いてよい（実利用者のデータは使わない）。
  - **認証情報や設定値は書かない。**

## 5. データ

| データ | 主な項目 | 相手から見えるか | 本人の権限 | 保存期間 | 区分 |
| --- | --- | --- | --- | --- | --- |
| LLM利用記録 | 所有者（ユーザー、または評価コマンド用の「システム」）、日時、プロンプト名、実行方式・モデル名、入力/出力トークン数、推定費用、結果（**成功／失敗／タイムアウト／上限超過／設定不足**）。**入力文・応答文は保存しない** | 見えない | 読み取りも書き込みもできない（サーバー側の処理だけが書く） | ユーザーの削除まで（Q-P4 仮置き） | システム記録 |
| 月次集計（D-012） | 年月（日本時間）、推定費用の合計、プロバイダへ送った呼び出しの回数。**ユーザーを特定する項目を持たない** | 見えない | どの利用者も読み書きできない | 削除の対象外（D-012） | システム記録 |

利用記録の扱い:
- 000a の「個人データを追加する手順」に従う。分離の仕組みに登録し、分離テストの共通部品でテストし、ユーザー単位の全データ削除の対象に加える。
- 「システム」所有の記録（評価コマンドの実行分）は、実在のアカウントを指さない固定の所有者値で持つ。どの利用者からも読めず、ユーザーの削除では消えない。

月次集計の扱い:
- 月間上限の判定に使う。ユーザーを削除しても合計が減らないので、削除と再登録で上限を回避できない（レビュー問い1への回答。D-012 で人間が承認）。
- 利用者分と「システム」分（評価コマンド）を区別せずに合算する。

## 6. AIの振る舞い

このSPECでは利用者向けのAI機能を作らない。作るのは呼び出しの共通部分だけ。

**共通部分とアダプタ**
- アプリ内のすべてのLLM呼び出しは、この共通部分1か所を通す。
- 実行方式のSDK・APIを直接呼ぶコードは、アダプタの中だけに置く。
- アダプタの共通の形（入力: プロンプト名・本文・モデル・最大出力トークン、出力: 応答文・トークン数・可能なら費用の目安・エラーの種類）を `app/README.md` に書く。
- 実行方式は設定（環境変数）で切り替える。MVP開発中に作るのは「モック」と「プラン方式」の2つ。
- **自動テスト実行時は、設定にかかわらずモックを使い**、外部に通信しない。ローカル起動でも、プラン方式の認証情報がなければモックで動く。
- モックはプロンプト名ごとに固定の応答を返す。テストから応答・失敗・遅延を指定できる。
- 使うモデルは設定で選ぶ（主案／代替。D-010）。

**プラン方式のアダプタの決まり**
- Agent SDK はエージェントとして動く仕組みなので、アプリからは「1回の文章生成」としてだけ使う。
  - **ツール（ファイルの読み書き、コマンド実行、Web取得、外部ツール連携など）はすべて無効にする。**
  - 開発機のプロジェクト設定・指示ファイル（このリポジトリの CLAUDE.md など）を読み込ませない。
  - システムプロンプトは `app/prompts/` のプロンプトだけを使う。
  - 1回の呼び出しで、モデルとのやり取りは1往復に限る。
  - 理由: 利用者の入力をきっかけに、AIがサーバー上のファイルや秘密情報に触れる経路をなくすため。
- プランの認証情報はサーバー側の環境だけに置く（環境変数、または開発機のログイン情報）。リポジトリ、ブラウザに届くコード・応答、ログ、評価結果には出さない。
- 実行方式が会話の記録を手元のファイルに保存する機能を持つ場合は、無効にする。無効にできない場合は、呼び出しのたびに削除する。どちらもできない場合は、保存される場所を `docs/architecture.md` に記録し、SPEC-001（実利用者の本文を送り始める）より前に戦略担当へ戻す。
- プラン側の上限（クレジットの使い切り、利用回数の制限）で拒否された場合の扱い:
  - 再試行しない。結果は「失敗」とし、エラーの種類で区別する。
  - 利用者向けには上限超過と同じ文言を返す。

**上限**（値は環境変数で持つ。**未設定・不正な値なら、実プロバイダへの呼び出しをすべて拒否する**）

プラン方式では金額の請求が来ないため、金額の上限は「請求額の上限」ではなく、プランのクレジット枠を使い切らないための「消費の目安」として持つ（D-010。D-007 の「月数千円」の目安を引き継ぐ）。

| 上限 | 内容 |
| --- | --- |
| 1ユーザーあたり1日の呼び出し回数 | 仮置きの初期値は30回（architecture.md の提案） |
| アプリ全体の月間推定費用 | 仮置きの初期値は「APIの定価で換算して3,000円相当」。評価コマンドの実行分も含める。値は Q-H11 で人間が確認する |
| 1回あたりの最大出力トークン数 | 仮置き 800 |

- **推定費用**: トークン数にモデル別の単価（APIの定価。入力・出力それぞれ）を掛け、為替レートで円にしたもの。
  - 実行方式が費用の目安を返す場合も、比較できるように単価による推定を正とする。
  - 単価と為替レートは設定値で持つ。**単価が設定されていないモデルは実プロバイダで呼ばない。**
  - 単価は価格改定時に人間が更新する。
- **日・月の区切り**は日本時間（JST）の 0:00 と、毎月1日の 0:00。
- **1日の回数に数えるもの**（レビュー問い2への回答・採用）:
  - 実際にプロバイダへ送った呼び出しだけを数える（結果が成功・失敗・タイムアウトのもの）。
  - 再試行は、元の呼び出しと合わせて1回と数える。
  - プロバイダを呼ばなかった拒否（上限超過・設定不足）は数えない。
  - 評価コマンドの実行分は1日の回数上限の対象にしない（月間には合算する）。
- **月間の判定と予約**: 月次集計を使う。
  - 呼び出し前に「入力の見込み＋最大出力トークン分」の費用を予約する。入力の見込みは保守的に見積もる（日本語は1文字を最大1トークンとみなし、システムプロンプトを含める）。
  - 呼び出し後に、実際のトークン数で確定する。
  - タイムアウトやエラーで実際のトークン数が分からない場合は、予約した見込みのまま確定する（少なく数えないため）。
- 上限を超えたら、プロバイダを呼ばずに決まったエラーを返す。
  - 利用者向けの文言は日本語の固定文（例：「今日はAIの利用上限に達しました。明日またお試しください」）。
  - 利用記録の結果は「上限超過」とする。
  - 上限・単価・認証情報が足りない場合の結果は「設定不足」とする。

**その他**
- タイムアウトは仮置きで30秒。
  - プラン方式は起動に時間がかかる場合があるため、開発担当が実測して変えてよい。変えた場合は `app/README.md` に値と理由を記録する。
  - 一時的な失敗は1回だけ再試行してよい。
- 呼び出しごとに、第5章の「LLM利用記録」を残し、月次集計に足し込む。
- **相談本文（入力・応答）は、アプリのログ、エラーログ、利用記録、月次集計のどこにも出さない。** エラー内容を記録する場合も、本文を含まない形（エラーの種類・コード）にする。
- プロンプトはコードに埋め込まず、`app/prompts/` のファイルから名前で読み込む。

**`app/prompts/` の置き場**
- `app/prompts/README.md` に形式を説明する（1ファイル1プロンプト。ファイル先頭に「対応SPEC番号・目的・版・最終更新日」を書く）。
- サンプルを1件置く（例：`_sample.md`。SPEC-000b の共通部分と評価コマンドの動作確認用で、受け取った文を短く言い換えるだけ）。
- 良い例: プロンプトに SPEC 番号と版があり、変更履歴を追える。
- 悪い例: プロンプト文がコード内の文字列に散らばっている。

## 7. 例外・エラー

| 状況 | 振る舞い |
| --- | --- |
| プラン方式の認証情報がない | ローカル起動・テストはモックで動く。プラン方式を指定した場合は呼び出しを拒否し、結果は「設定不足」。エラーに認証情報の値は表示しない |
| 上限を超えている | プロバイダを呼ばずに決まったエラー。結果は「上限超過」 |
| 上限・単価が未設定または不正 | プロバイダを呼ばずに決まったエラー。結果は「設定不足」 |
| タイムアウト・プロバイダの一時的なエラー | 1回まで再試行し、その後は決まったエラー。本文をログに出さない |
| プラン側の上限による拒否（クレジットの使い切りなど） | 再試行しない。結果は「失敗」（エラーの種類で区別）。利用者向けには上限超過と同じ文言 |
| 存在しないプロンプト名 | 決まったエラー（開発者向け）。プロバイダを呼ばない |
| 評価コマンド: 認証情報がないまま実LLMを指定 | 何も送信せずにエラーで止まる |
| 評価コマンド: 推定最大消費が月間上限の残りを超える | 実行しない |
| 評価コマンド: eval-cases.md の表が読めない、または該当IDがない | 何も送信せずにエラーで止まる |

## 8. 受入基準（品質担当が判定する）

- [ ] AC-1（v1 AC-1 を拡張）: 実行方式のSDK・APIを直接呼ぶコードが、アダプタの中にしかない。モックとプラン方式の2つのアダプタが同じ共通の形を持ち、設定だけで切り替わる。共通の形が `app/README.md` に書かれている。（確かめ方: SDK名を `app/` 全体でgrep、自動テスト、文書確認）
- [ ] AC-2: 実行方式がプラン方式に設定されていても、自動テスト実行時はモックが使われ、外部に通信しない。モックはプロンプト名ごとの固定応答を返す。（確かめ方: 自動テスト。外部通信を遮断した状態でも通る）
- [ ] AC-3（v1 から一般化）: 目印になるダミーの認証情報を設定してブラウザ向けのビルドを作っても、成果物にその値も、認証情報の環境変数名も含まれない。（確かめ方: 自動テスト、またはスクリプトでビルド成果物をgrep）
- [ ] AC-4: 1日の回数上限・月間上限を小さく設定すると、上限に達した後の呼び出しはプロバイダ（モック）を呼ばずに決まったエラーを返し、結果は「上限超過」になる。次の場合は実プロバイダへの呼び出しがすべて拒否され、結果は「設定不足」になる。（確かめ方: 自動テスト）
  - 上限の設定を消した、または不正な値にした場合
  - 単価が未設定のモデルを指定した場合
  - 認証情報がない場合
- [ ] AC-5: 日の境界は日本時間0:00、月の境界は日本時間の毎月1日0:00で切り替わる（例：日本時間23:59に上限に達した利用者が、0:00以降は再び呼べる）。（確かめ方: 時刻を固定した自動テスト）
- [ ] AC-6: 月間上限の残りが1回分の見込み費用に満たないときは、同時に複数の呼び出しが来ても、確定後の合計が月間上限を超えない。（確かめ方: 自動テスト）
- [ ] AC-7（v2 で追加）: 1日の回数は次のとおり数える。（確かめ方: 自動テスト）
  - 成功・失敗・タイムアウトの呼び出しは1回と数える。
  - 再試行した呼び出しも1回と数える。
  - 上限超過・設定不足で拒否した呼び出しは数えない。
  - 評価コマンドの実行は1日の回数に数えず、月次集計には加わる。
- [ ] AC-8: 呼び出しごとに、第5章の項目で利用記録が1件残る。結果の値は5種類（成功／失敗／タイムアウト／上限超過／設定不足）のいずれかで、入力・応答の本文は含まれない。（確かめ方: 自動テスト）
- [ ] AC-9（v2 で拡張）: 000a の分離テストの共通部品を使い、次を確かめる。（確かめ方: 自動テスト。共通部品への追加が数行で済んでいることもコードで確認）
  - ユーザーAの利用記録を、ユーザーB・Aの連携相手・匿名の権限から読めず、変更・削除もできない。
  - **A本人の権限でも読み書きできない。**
  - 月次集計は、どの利用者の権限からも読み書きできない。
  - 全データ削除でAの利用記録は消え、他ユーザーと「システム」の記録は変わらない。
  - **削除の前後で月次集計の合計（費用・回数）が変わらない**（D-012）。
- [ ] AC-10: 目印の文字列を含む入力で、成功・プロバイダのエラー・タイムアウト・上限超過の4経路の呼び出しを行う。テスト中に出力されたアプリのログ（標準出力・エラー出力を含む）、利用記録、月次集計のどこにも目印が現れない。（確かめ方: 自動テスト）
- [ ] AC-11（v2 で追加）: プラン方式のアダプタは、すべてのツールを無効にし、プロジェクトの設定・指示ファイルを読み込まず、`app/prompts/` のプロンプトだけをシステムプロンプトとして、1往復で呼び出す設定になっている。会話記録の手元保存は、無効にするか呼び出しごとに削除している（できない場合は `docs/architecture.md` に記録がある）。（確かめ方: アダプタが実行方式に渡す設定を検証する自動テスト（SDK部分はモック）とコード確認。実LLMでの初回評価の後に、手元に会話記録が残っていないことを品質担当または人間が確認する）
- [ ] AC-12: 次をすべて満たす。（確かめ方: 自動テストとファイル確認）
  - プロンプトは `app/prompts/` のファイルから名前で読み込まれる。
  - 存在しない名前では、プロバイダを呼ばずにエラーになる。
  - `app/prompts/README.md` とサンプル1件がある。
  - サンプルの先頭に、SPEC番号・目的・版がある。
