# SPEC-000a: 技術基盤 — 雛形・認証・分離・削除・テスト（v1）

- 状態: レビュー中（技術選定 Q-H10 の人間承認が `docs/decisions.md` に記録されるまで実装しない）
- 関連: 総括 [SPEC-000](SPEC-000.md) v2（目的、第2-A章の技術要件、第5章のデータ原則）、戦略 第8章、決定 D-003 / D-004 / D-006 / D-008、未決 Q-P4 / Q-P5 / Q-P8 / Q-P9 / Q-U1
- 由来: SPEC-000 v1 の範囲 1〜5・9・10、AC-1〜AC-12・AC-22〜AC-25 を分割。レビュー（docs/reviews/spec-review-SPEC-000-v1.md）の問い1・3・4 と軽微点を反映
- 後続: SPEC-000b はこのSPECの分離・削除の仕組みの上に載る

## 1. 目的

スマホで開けるPWAの雛形に、ログインと「他人のデータを読めない仕組み」をデータ層で入れる。以後のSPECが個人データを追加するとき、決まった手順と共通テストに従うだけで非公開性を守れるようにする。

## 2. 範囲

- 含む:
  1. PWAの雛形（Webアプリのマニフェスト、ホーム画面への追加、スマホ幅のレイアウト）と最小画面（新規登録・ログイン・空のホーム・該当ページなし）
  2. 認証：新規登録、ログイン、ログアウト、未ログイン時の保護（画面・API）
  3. データ層でのユーザー分離と、分離テストの共通部品
  4. データ：アカウント、プロフィール、連携（pair）の器（UIなし）
  5. ユーザー単位の全データ削除処理（サーバー側の関数のみ）
  6. テストの仕組み（ローカルの1コマンドで全テスト）
  7. `.env.example`、`app/README.md`（ローカル起動手順、前提ソフト、テストコマンド、**個人データを追加する手順**）
- 含まない: LLM関連すべて（SPEC-000b）、総括 SPEC-000 第2章「含まない」の各項目（特に、登録時のアカウント有無を隠す動作・メール確認・パスワード再設定・セッション有効期間の上限設定は公開準備SPEC）

## 3. 利用者の流れ

総括 SPEC-000 第3章の1〜4。

## 4. 画面・入出力

全画面共通: 日本語表示。幅 375px〜430px で横スクロールが出ない。文字入力欄の文字サイズは16px以上。ボタンと、ボタンとして使う文字リンク（「新規登録はこちら」など）のタップ領域は縦横44px以上。

| 画面 | 表示・入力 | ボタン | エラー表示 |
| --- | --- | --- | --- |
| ログイン | 認証方式に応じた入力（例：メールアドレス、パスワード） | ログイン、「新規登録はこちら」 | 認証失敗時は「メールアドレスまたはパスワードが正しくありません」のように、**アカウントの有無を区別しない** 文言。通信失敗時は「通信できませんでした。電波の良い場所でもう一度お試しください」 |
| 新規登録 | 認証方式に応じた入力、表示名（任意・20文字以内）、「18歳以上です」チェック（必須） | 登録、「ログインはこちら」 | 未入力・形式誤りは該当欄の下に表示。チェックなしでは登録しない。**登録済みのメールアドレスでの登録時に「登録済み」と分かる応答になることは、公開前まで許容する**（仮決定 Q-P9。理由は下記）。その場合も既存アカウントへのログインや情報の表示は起こらない |
| ホーム（ログイン後） | アプリ名「CCAI（仮称）」、表示名（あれば）、「相談機能は準備中です」 | ログアウト | — |
| 該当ページなし | 「ページが見つかりません」 | ホームへ（未ログインならログインへ） | — |

API（画面から使うもの）: 未ログインの要求には、データを含まない「認証が必要」の応答（HTTPなら401）を返す。

**問い1への回答（登録時の重複通知）**: 採用（developer 提案どおり、条件つき）。
- 理由: 登録時に有無を隠すにはメール確認とメール送信サービス（費用・外部へのデータ送信）が要り、000a の範囲を超える。000a の期間の利用者は開発者本人と招待した少数で、公開もしない。
- ただしこのアプリでは「相手が自分のメールアドレスで登録を試し、パートナーが利用しているかを知る」ことが非公開性の問題になる。そのため **公開前の必須条件** とし、公開準備SPECでメール確認と同時に解消する。人間の確認事項として Q-P9 に「仮決定」で残す。ログイン時の区別しない文言（AC-5）は 000a で必須。

## 5. データ

総括 SPEC-000 第5章の原則に従う。

| データ | 主な項目 | 相手から見えるか | 本人の権限 | 保存期間 | 区分 |
| --- | --- | --- | --- | --- | --- |
| アカウント | 認証用の識別子（メールアドレス等）、作成日時 | 見えない | 認証基盤経由のみ | 削除するまで（仮置き Q-P4） | 本人申告 |
| プロフィール | 表示名（任意）、18歳以上の確認日時 | 見えない（相手への表示名の公開は SPEC-003 で決める） | 読む・書く | 削除するまで（仮置き Q-P4） | 本人申告 |
| 連携（pair）の器 | 連携ID、状態、作成日時、メンバー | 連携の存在のみ当事者2人に見える（UIは SPEC-003） | 000a では作成・変更の画面・APIなし（テスト用の作成手段のみ） | 解除・削除まで（仮置き Q-P5） | システム記録 |

**pair の最小制約（問い3への回答。採用。SPEC-003 で変えてよい）**
- メンバーは最大2人。
- 1人が同時に所属できる `active` の pair は1つ。
- 状態は `active` / `ended` のみ。
- 制約はデータ層（DBの制約など）で表す。
- pair への所属は、相手の個人データを読む権限を一切与えない。

**個人データを追加する手順**（`app/README.md` に書く。後続SPECはこれに従う）
1. 所有者を示す列を持たせる。
2. 分離の仕組み（総括 第2-A章 T-2）に登録する。新しいテーブル等に既定で付く不要な権限があれば取り消す。
3. 分離テストの共通部品で、AC-9・AC-10 相当のテストを追加する。
4. ユーザー単位の全データ削除処理の対象に加え、AC-12 相当のテストを追加する。
5. 分離を迂回する特権（管理用の鍵・接続）は、決められたサーバー側の部品からだけ使う。

## 6. AIの振る舞い

なし（AIを使わない）。

## 7. 例外・エラー

| 状況 | 振る舞い |
| --- | --- |
| 未ログインで保護された画面・APIにアクセス | 画面はログインへ移動、APIは401でデータを返さない |
| ログイン情報の誤り | アカウントの有無を区別しない文言 |
| 登録済みメールでの新規登録 | 「登録済み」と分かる応答は許容（Q-P9 仮決定）。既存アカウントにはログインさせず、既存アカウントの情報も表示しない |
| 登録ボタンの連打 | アカウントが二重に作られない |
| セッション切れ | 次の操作でログイン画面へ。セッションの有効期間は認証方式の標準のまま（上限設定は公開準備SPEC。Q-P8） |
| 通信失敗 | 第4章の通信失敗の文言。画面が固まらない |
| ログアウト後に戻るボタン | ホームの内容を表示しない（ブラウザ・Service Worker のキャッシュから個人の情報を出さない） |
| pair の制約違反（3人目、2つ目の active） | データ層で拒否される |

## 8. 受入基準（品質担当が判定する）

**テスト・起動**
- [ ] AC-1（旧AC-1）: `app/README.md` に書かれた1つのコマンドで全自動テストが走り、**`.env` なし・LLMのAPIキーなし** の状態で失敗0件で終わる。このコマンドは、テストに必要なローカルのDB等の起動を含むか、README の手順で事前に起動したうえで1コマンドで済む。前提ソフト（コンテナ環境など）は README に明記されている。（確かめ方: 品質担当が `.env` を置かない状態で実行）
- [ ] AC-2（旧AC-2）: `app/README.md` の手順だけで、ローカルでアプリを起動しログイン画面を表示できる。有料サービスの契約や外部サービスのアカウント作成は不要。（確かめ方: 品質担当が手順どおりに実行し画面確認）
- [ ] AC-3（旧AC-3）: `.env.example` に、000a で必要な環境変数がすべて説明つきで並び、実際のキーやパスワードの値を含まない（ローカル開発用に公開されている既定値は可。その旨を注記）。`.env` はgit管理外である。（確かめ方: ファイル確認と `.gitignore` 確認、キーらしき文字列のgrep）

**認証**
- [ ] AC-4（旧AC-4）: 「18歳以上です」にチェックしないと登録できず、チェックすると登録されてホームに移る。登録ボタンを連続で押してもアカウントは1件だけ作られる。（確かめ方: 自動テスト）
- [ ] AC-5（旧AC-5）: 正しい情報でログインするとホームが表示され、存在しないアカウントと誤ったパスワードの両方で同じ文言が出る。（確かめ方: 自動テスト）
- [ ] AC-6（旧AC-6）: 未ログインでホームを開くとログイン画面に移り、保護されたAPIは401を返して本文にユーザーのデータを含まない。（確かめ方: 自動テスト）
- [ ] AC-7（旧AC-7）: ログアウト後、ログアウト前のセッション情報で保護APIを呼ぶと401になる。ログアウト後にブラウザの戻るボタンでホームの内容（表示名を含む）が表示されない。（確かめ方: APIは自動テスト、戻るボタンは画面確認）
- [ ] AC-8（旧AC-8）: ブラウザで動くスクリプトから、セッションの認証情報（トークン）を読めない。cookieを使う場合は HttpOnly と SameSite（Lax以上）が付き、本番用の設定では Secure も付く。（確かめ方: 自動テストまたは設定の確認。選定した基盤の標準構成でこれを満たせない場合は、実装の最初に確認し、満たせないことが分かった時点で実装を止めて戦略担当へ戻す）

**データ分離・削除**
- [ ] AC-9（旧AC-9）: ユーザーAのプロフィールを、ユーザーBとして（ID指定、一覧、更新、削除のいずれでも）読めず変更・削除できない。この確認は画面・APIを経由したテストに加え、**データ層を直接呼ぶテスト**（Bの権限・文脈で、Aのデータを対象に呼ぶ）でも行い、0件または拒否になる。未ログイン（匿名）の権限でも同じ。（確かめ方: 自動テスト）
- [ ] AC-10（旧AC-10）: テスト用にAとBを同じ `active` の pair に登録した状態でも、AC-9 と同じ結果になる。（確かめ方: 自動テスト）
- [ ] AC-11（旧AC-11）: 分離テストは共通部品になっており、個人データの種類を1つ追加するときに数行の追加で AC-9・AC-10 相当のテストを適用できる。第5章「個人データを追加する手順」が `app/README.md` に書かれている。（確かめ方: コードと文書の確認。000b で実際に使われることで再確認する）
- [ ] AC-12（旧AC-12）: ユーザー単位の全データ削除処理を呼ぶと、そのユーザーのアカウント・プロフィール・pair の所属がすべて消え、他のユーザーのデータは1件も変わらない。（確かめ方: 自動テスト）
- [ ] AC-13（新）: pair の制約（メンバー最大2人、1人が同時に所属できる `active` は1つ、状態は `active` / `ended` のみ）に反する登録がデータ層で拒否される。（確かめ方: 自動テスト）
- [ ] AC-14（新）: 分離を迂回する特権（管理用の鍵・接続）を使うコードが、決められたサーバー側の部品の中にしかない。その鍵の値も環境変数名も、ブラウザ向けのビルド成果物に含まれない。（確かめ方: grep と、ダミー値を設定したビルド成果物のgrep）

**PWA・画面**
- [ ] AC-15（旧AC-22）: 幅375pxで、ログイン・新規登録・ホームに横スクロールが出ず、入力欄の文字は16px以上、ボタンとボタンとして使う文字リンクのタップ領域は縦横44px以上。（確かめ方: 品質担当がブラウザの開発者ツールのスマホ表示で画面確認）
- [ ] AC-16（旧AC-23）: Webアプリのマニフェスト（名前「CCAI（仮称）」、アイコン、起動URL、表示モード）があり、Android Chrome でインストール可能と判定され、iOS Safari でホーム画面に追加して起動できる。（確かめ方: 開発者ツールのマニフェスト確認。実機での追加は人間が画面確認）
- [ ] AC-17（旧AC-24）: Service Worker を使う場合、ログイン後の画面とAPI応答をキャッシュしない。ログアウト後にオフラインでアプリを開いても、表示名などの個人の情報が表示されない。（確かめ方: コード確認と画面確認）

**範囲**
- [ ] AC-18（旧AC-25）: 第2章「含まない」の機能（LLM関連、相談、連携UI、通知、退会画面、パスワード再設定など）や、承認されていない外部サービス（エラー監視、解析、メール送信など）が組み込まれていない。（確かめ方: コードと依存関係の確認）
