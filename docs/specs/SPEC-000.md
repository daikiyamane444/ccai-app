## 1. 目的

MVP（D-004）の後続SPEC（001 個別相談＋安全経路、002 言語化支援、003 アカウント連携、004 伝え直し＋送信前確認、005 時間差伝達・通知、006 簡易問診）がすべて載る土台を作る。
利用者向けの機能はまだ作らない。代わりに、**一人ひとりの相談が他人に読まれない仕組み**と、**LLMを安全・低費用で呼ぶ共通部分**を最初に固め、以後のSPECが同じ仕組みを使うだけで非公開性と費用上限を守れるようにする。

技術そのもの（フレームワーク、DB製品、認証方式、ホスティング、LLM製品）はこのSPECでは決めない。第2-A章の要件・評価基準に沿って developer が `docs/architecture.md` に選定案を書き（v1 作成済み・承認待ち）、人間が承認する（CLAUDE.md 技術選定ゲート）。

## 2-A. 技術選定が満たすべき要件と評価基準（developer が `docs/architecture.md` で使う）

**必須要件**（満たさない候補は推奨案にしない）

| ID | 要件 |
| --- | --- |
| T-1 | iOS Safari・Android Chrome の最新版でスマホ表示でき、ホーム画面に追加できるPWAを作れる（D-006） |
| T-2 | ユーザーごとのデータ分離を **データ層で** 強制できる（例：DBの行単位のアクセス制御、またはすべての読み書きが所有者条件を必ず通るデータアクセス層）。画面やAPIの個別実装の注意だけに頼らない。分離を迂回できる特権（管理用の鍵・接続など）を使う場合は、サーバー側の限定した部品だけに置ける |
| T-3 | パスワードの保存・照合やセッション管理を自前で実装せず、実績のあるライブラリまたはサービスを使う。将来のパスワード再設定・メール確認に対応できる |

| T-5 | LLMプロバイダが、API経由の入力・出力を **モデルの学習に使わない**（既定または設定で）ことを規約・公式文書で確認できる。確認した文書のURLと日付を記載する |

## 2-B. 基盤側ログの確認の割り振り（決定事項ではなく、戦略担当の割り振り）

- 000a / 000b はローカルのみで動き、相談本文をまだ扱わない。000b の受入基準は **アプリのログと利用記録** に本文が出ないことまでを確かめる。
- **SPEC-001**（相談本文の保存・LLM送信が始まる）の受入基準に、次を必須として入れる：選定した DB・認証基盤・ホスティングの、リクエストログ・クエリログ・エラー記録・管理画面の記録に、目印を含む相談本文が残らないこと（ローカル環境で確かめ、公開先の基盤で確かめられない点は「公開前に確認」として残す）。残る場合は設定で止めるか、残る経路を `docs/architecture.md` に記録して人間に判断を求める（Q-P7）。
- 公開（Q-H8）の前に、公開先の基盤で同じ確認を行う（公開準備SPEC）。

## 3. 利用者の流れ

1. スマホのブラウザでアプリを開く → 未ログインならログイン画面が出る。
2. 「新規登録」→ 認証方式に応じた入力、表示名（任意）、「18歳以上です」のチェックで登録 → ホームへ。
3. ホームには「CCAI（仮称）」の名前、「相談機能は準備中です」程度の案内、ログアウトボタンだけがある。
4. ログアウト → ログイン画面に戻る。次回はログイン画面から入る。ホーム画面に追加してアプリのように起動できる。

開発者向け: `app/README.md` の手順でローカル起動し、1コマンドで全テストを実行する。評価コマンドはまず試走（モック）で動かし、人間が承認したAPIキーと費用上限を設定したうえで実LLMで流す。

## 5. データ（全SPEC共通の原則）

- すべての個人データは **所有者1人（owner）** に属する。
- 二人の連携（pair）は、相手の個人データを読む権限を **一切与えない**。
- 相手に見えるデータは、SPEC-004 で作る「本人が承認した伝達文」だけに限り、個人データとは別の保存場所に置く。
- 個人データを追加するSPECは、000a の「個人データを追加する手順」（所有者列、分離の仕組みへの登録、分離テスト、全データ削除の対象への追加）に従う。
- 相談由来の記録には区分（本人申告／相手の報告／推測／AI仮説）を持たせる（列の具体化は SPEC-001 以降）。
- 保存期間は「削除するまで」を仮置き（Q-P4）。
- 個別のデータ項目は 000a 第5章・000b 第5章。
