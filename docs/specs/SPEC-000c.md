## 1. 目的

人間本人だけが、iPhone と PC のブラウザから HTTPS の個人用URLで 000a の機能（登録・ログイン・ログアウト・ホーム）を使え、iPhone のホーム画面に追加できるようにする（D-013）。

あわせて、000a がテスト用の互換層（shim）と偽の認証基盤で確かめた点を、本物の Supabase と Vercel の上で確かめ直す（architecture.md 11-2、QA の追加推奨）。そのうえで、後続SPEC（相談本文を扱う SPEC-001）の土台が実サービスでも成り立つことを示す。

## 2. 範囲

### 含む

1. **公開の構成**
   - Vercel（Hobby・無料。関数の実行地域は東京）
   - Supabase クラウド（東京リージョン、Free プラン）
   - GitHub の非公開リポジトリ（Vercel はここから取り込む）
2. **新規登録を本人のメールアドレスだけに限定する**（D-013）
   - 方式（戦略担当の判断）: サーバー側の設定値に「登録を許すメールアドレスの一覧」を持つ。一覧にないアドレスでの登録は、Supabase に送る前に拒否する。
   - 一覧が空・未設定なら、登録は全部拒否する（fail closed）。
   - 比較は前後の空白を除き、大文字・小文字を区別せずに行う。
   - 拒否の文言は、一覧の有無や中身が分からない固定文にする（例：「現在、新規登録を受け付けていません」）。
   - Supabase 側の追加の守り: 公開用キーはブラウザに出ない構成（000a）なので、Supabase の登録窓口を外から直接呼ぶ手段はない。これをビルド成果物と公開URLの検査で確かめる（AC-5、AC-17）。
3. **000a 検収の持ち越しの修正**（第2-A章の判断どおり）
   - A-1（必須）、A-2〜A-6、A-8 の整理
4. **最小権限のDB接続ロール**（A-6・QA追加2）
   - アプリと結合テストは、テーブル権限も BYPASSRLS も持たないログインロールで接続する。
   - そのロールは `anon`／`authenticated`／`service_role` への `SET ROLE` だけができる。
   - ロールの作成は、マイグレーションのSQLに入れる。パスワードはSQLに書かず、人間が手順書に従って設定する。
5. **検索エンジンに載せない**
   - 全ページに `noindex` を付ける（応答ヘッダーまたはメタタグ）。
   - `robots.txt` で全体のクロールを拒否する。
   - 理由: 個人用URLのため。
6. **本物のサービスでの結合テスト**（GitHub Actions。手動起動のみ。第2-B章）
7. **人間向けの作業手順書** `docs/runbooks/deploy-personal.md`（developer が作る。要件は付録A）
8. `app/README.md` と `.env.example` への追記
   - 追記する環境変数: 登録許可の一覧、DB接続ロール、関数の地域など
   - あわせて、デプロイと結合テストの説明

- 基盤側ログに相談本文が残らないことの確認（SPEC-001。総括 第2-B章）。000c の時点では相談本文がまだ存在しない

## 2-B. 本物のサービスでの確かめ方（GitHub Actions の採否）

**採否: 採用する。ただし人間の承認（Q-H14）が前提。**
- 採る理由: AI の作業環境は Supabase・Vercel に直接つながらない。全部を人間の画面確認にすると、非エンジニアの人間に SQL や開発者ツールの作業が大量に生じる。
- GitHub Actions の実行環境からなら、本物の Supabase と公開URLに接続できる見込みがある（未確認。最初の実行で確かめる）。
- AI は github.com に接続できるので、手動起動と結果（ログ）の読み取りができる。

**決まり**
- 起動は手動のみ（`workflow_dispatch`）。push のたびには動かさない。
- 想定の消費は1回数分。無料枠（非公開リポジトリは月2,000分）で収める。期限切れトークンの確認（AC-12）は約65分待つため、別の手動ジョブにして1回だけ流す。
- **使う秘密情報**: Supabase のプロジェクトURL、公開用キー、管理用キー、アプリ用DB接続ロールの接続情報、公開URL。
  - 人間が GitHub のリポジトリ設定（Secrets and variables → Actions）に入力する。
  - AI は値を見ない。
  - ワークフローは値をログに出さない（GitHub の伏せ字に頼るだけでなく、出力しない書き方にする）。
  - Postgres の管理者（`postgres`）のパスワードは CI に渡さない。
- **テスト用ユーザー**:
  - 管理APIで作る（メールは送られない）。メールアドレスは、配信されないドメインに実行IDを含めた決まった形（例：`ccai-ci+<実行ID>-<n>@example.invalid`。Supabase が受け付けない場合は開発担当が別の配信不能な形を選び、手順書に記録する）。
  - 後片付け: 終了時（失敗時も）に、その実行で作ったユーザーだけを管理APIで削除する。あわせて、前の実行の取り残し（決まった形のアドレスだけ）も削除する。
- **本番データへの影響**:
  - 結合テストは、人間の個人用プロジェクトそのものに対して流す。テスト用に2つ目のプロジェクトは作らない。理由: 人間の作業を減らすため。また、この時点の本番データは本人のアカウント1件だけで、相談本文がない。
  - 守り:
    - テストは、決まった形のアドレスのユーザーにだけ触れる。
    - テストの最初と最後に「決まった形以外のユーザーの件数」と「それらのプロフィール・所属の件数」を比べ、変わっていたら失敗にする。
    - マイグレーションの適用や設定の変更はしない。
  - 相談本文を保存する SPEC-001 より前に、この方式を続けるか、テスト専用プロジェクトに分けるかを決める（Q-H13）。
- **人間が承認しない場合（Q-H14 が「不採用」）の代わり**:
  - AC-8〜AC-17 の「CI」の項目は、人間が手順書の付録SQL・操作で確かめる形に置き換える（手順書に両方を用意する）。
  - 期限切れトークンの確認（AC-12）は、人間の画面確認（ホームを1時間以上開いたままにしてからログアウト）で行う。

## 2-C. 費用0円の前提と、止めて人間に聞く条件

前提: Vercel Hobby、Supabase Free、GitHub Free（非公開リポジトリ、Actions は無料枠内）。いずれもクレジットカードの登録は不要と想定する（未確認。手順書の作成時に開発担当が公式ページで確認する）。

次のどれかに当たったら、**作業を止めて問い合わせ担当経由で人間に聞く**（AI・人間とも先に進めない）。
- 画面でクレジットカードの登録、有料プランへの切替え、支払い方法の入力を求められた。
- 必要な設定が有料プランでしか使えないと分かった。例: Vercel の関数地域を東京に指定できない、最小権限ロールを接続方式の都合で使えない、など。
- Supabase の使用量の表示、または GitHub Actions の利用時間が、無料枠の50%を超えた。
- Supabase の Free プロジェクトの数が上限に達しており、新しく作れない。
- 規約の確認で、個人の検証用途でも無料プランが使えないと読める記述が見つかった。

補足: 最小権限ロールが使えない場合（A-6）は、代わりに既定の `postgres` ロールで接続し、RLS は 000a と同じく `SET LOCAL ROLE` で効かせる。この方式に進むかは人間が決める。決まった場合は `docs/architecture.md` に記録し、SPEC-001 より前に再検討する。

## 3. 利用者の流れ（人間本人）

1. 手順書に沿って、各サービスのアカウント作成と設定を行う（付録A）。
2. 開発担当が修正したコードが品質担当の検収に合格する。問い合わせ担当が人間の了承を得たうえで、コードが非公開リポジトリに入る（Q-H14）。Vercel が自動で取り込み、個人用URLが発行される。
3. PC のブラウザで個人用URLを開き、本人のメールアドレスで新規登録する。ログアウトとログインを試す。
4. iPhone の Safari で同じURLを開いてログインし、ホーム画面に追加する。追加したアイコンから起動する。
5. 手順書の確認チェックリストに OK／NG を付け、問い合わせ担当に伝える。秘密情報は伝えない。

## 4. 画面・入出力

画面は 000a のまま。変更点は次の2つ。
- **新規登録**: 許可の一覧にないアドレス、または一覧が未設定のとき、「現在、新規登録を受け付けていません」を表示する。アカウントは作らない。入力欄の検証エラー（形式誤り、18歳以上の未チェック）は、従来どおり先に表示してよい。
- **ログアウト**: 期限切れのアクセストークンでも、認証基盤側のセッションが確実に失効する（A-1）。画面の文言は変えない。

**結合テスト（CI）の出力**
- GitHub Actions のログに、項目ごとの OK／NG と件数だけを出す。
- 秘密情報、メールアドレス（テスト用を除く）、トークンは出さない。

## 5. データ

- 新しい個人データのテーブルは作らない。
- 追加するのはDBのロールと権限だけ（マイグレーションSQL）。
  - アプリ用ログインロール: テーブル権限なし、BYPASSRLS なし。`anon`／`authenticated`／`service_role` への SET ROLE だけができる。
  - 既存のテーブル・ポリシーは変えない。
- 登録許可の一覧は、Vercel の環境変数に置く（サーバー側だけ）。リポジトリ・ブラウザ・ログには出さない。
- 保存地域: Supabase は東京（D-011）。Free プランには自動バックアップがない（architecture.md E-6）ので、バックアップの保存地域は「該当なし」として記録する。
- 削除: 本物の Supabase で、アカウント削除の連鎖を確かめる（AC-11）。

## 6. AIの振る舞い

なし（LLMを使わない）。

## 7. 例外・エラー

| 状況 | 振る舞い |
| --- | --- |
| 許可の一覧にないアドレスで登録 | 固定文で拒否。Supabase に送らない。アカウントを作らない |
| 許可の一覧が空・未設定 | 登録は全部拒否（fail closed）。ログインは従来どおり使える |
| 期限切れのアクセストークンでログアウト | 認証基盤側のセッションを確実に失効させる。失効に失敗した場合も cookie は消し、エラーの種類だけをログに出す（000a と同じ）。旧 cookie で戻れない |
| アプリ用ロールが SET ROLE をし忘れた処理 | 権限エラーで失敗する（分離なしで動かない） |
| Supabase の Free プロジェクトが無操作で一時停止 | 画面は「通信できませんでした…」（000a の文言）。手順書に再開の方法を書く |
| 結合テストの途中で失敗 | 後片付け（テスト用ユーザーの削除）は必ず行う。後片付け自体が失敗したら、ジョブを失敗にして、残ったユーザー数をログに出す |
| 結合テストで、テスト用以外のユーザー・データの件数が変化した | ジョブを失敗にし、それ以上の操作をしない。問い合わせ担当から人間に報告する |
| 費用が発生しそうな画面・設定 | 第2-C章のとおり止めて人間に聞く |

## 8. 受入基準（品質担当が判定する）

人間が確かめる項目は、手順書の確認チェックリストに同じ番号で載せる。人間の OK／NG の報告を、品質担当が判定の根拠にする。

## 付録A. 人間向け作業手順書（`docs/runbooks/deploy-personal.md`）の要件

開発担当が作成する。手順の画面名・ボタン名は、作成時に各サービスの公式ドキュメントで確かめる。確かめられなかったものは、その旨を書く。

### A-1. 全体の形

- 非エンジニアが、PC のブラウザだけで、1手順ずつ進められる粒度にする。ターミナル（コマンド入力）は使わない。
- 各手順に次の6点を書く。
  1. 目的（1行）
  2. 開くURL
  3. 押すボタン・選ぶ項目（画面に出る英語表記のまま。日本語の説明を添える）
  4. 入力する値（秘密情報の場合は「どこからコピーして、どこへ貼るか」だけを書く）
  5. 終わったときに見えるはずの画面（期待結果）
  6. うまくいかないときの対処、または「ここで止めて問い合わせ担当に連絡」
- 手順は番号つきで、途中で中断しても再開できるように、区切り（チェックポイント）を置く。
- 冒頭に、所要時間の目安、必要なもの（PC、iPhone、本人のメールアドレス、パスワード管理の方法）、費用が0円であることの前提と、第2-C章の「止める条件」を書く。

### A-2. 含める手順（この順を基本とし、依存関係に合わせて開発担当が調整してよい）

1. GitHub のアカウント作成（既にあれば省略）。非公開（Private）リポジトリの作成。AI がコードを入れるための接続の許可（方式は Q-H14 の回答に合わせて問い合わせ担当と決める）。
2. Supabase のアカウント作成と、プロジェクトの作成。
   - リージョンは Northeast Asia (Tokyo)、プランは Free。
   - DBパスワードは自動生成させ、パスワード管理の場所に保存する。
3. Supabase の設定。
   - Auth のメール確認をオフにする。
   - Data API（REST／GraphQL）を無効にするか、`public` を公開対象から外す。
   - 新規登録の設定は、アプリの登録が動く状態のままにする（登録の限定はアプリ側で行う）。
4. マイグレーションSQLの適用。
   - GitHub の画面でSQLファイルを開いてコピーし、Supabase の SQL Editor に貼り付けて実行する。
   - 複数ファイルなら順番を明記する。
   - 実行後に確認するもの（表の一覧など）も書く。
5. アプリ用DB接続ロールのパスワード設定。
   - パスワードはSQLの中で生成して画面に1回だけ表示する方式にする。または、Supabase の画面の機能で生成する方式でもよい。
   - **人間が文字列を手で組み立てる作業を最小にする**。例: 接続情報を部品ごとの環境変数に分ける。少なくとも、組み立て済みの形の例（伏せ字入り）を示す。
6. Vercel のアカウント作成（GitHub でログイン）と、リポジトリの取り込み。
   - アプリのフォルダ（`app/`）をルートに指定する。
   - 関数の実行地域が東京になっていることを確認する（設定ファイルで指定し、画面で確認するだけにする）。
7. Vercel の環境変数の設定。
   - 変数名の一覧と、それぞれの値をどこからコピーするか。
   - 登録許可の一覧には本人のメールアドレスを入れる。
   - ブラウザに渡す種類の変数（`NEXT_PUBLIC_`）は作らない。
8. GitHub Actions の秘密情報の設定（Q-H14 で採用の場合）。
   - Vercel と同じ値を、どこからコピーしてどこへ貼るか。
9. 最初のデプロイの確認と、個人用URLの控え。
   - URL は秘密情報ではないが、むやみに共有しない旨を書く。
10. PC での確認。
    - 新規登録、ログアウト、ログイン、戻るボタン。
    - 開発者ツールで `document.cookie` を確かめる手順（キー操作を具体的に書く）。
11. iPhone での確認。
    - Safari で開いてログインする。
    - 共有ボタンから「ホーム画面に追加」する。
    - アイコンから起動し、戻る・機内モード・PC でのログアウトの影響を確かめる（AC-19〜23）。
12. 確認チェックリスト。
    - 第8章の「人間・管理画面」「人間・画面」の項目を、AC番号つきで並べる。
    - 各項目に OK／NG と、NG のときの様子を書く欄を設ける。
13. 運用メモ。
    - Supabase の Free プロジェクトが1週間使わないと一時停止すること、その再開方法。
    - 秘密情報を漏らしたかもしれないときに、キー・パスワードを作り直す手順。
    - PC でログアウトすると iPhone もログアウトされること。
    - 個人用URLを他人に教えないこと。

### A-3. 秘密情報の扱い（手順書の冒頭と、該当する各手順に書く）

- 秘密情報とは次のものを指す。
  - Supabase の公開用キー・管理用キー
  - DBのパスワードと接続文字列
  - アプリ用ロールのパスワード
  - 本人のアカウントのパスワード
- **チャット（Claude を含む）、メール、メモアプリ、スクリーンショット、GitHub の Issue やファイルに貼らない・写さない。**
- 入力してよい場所は次の3つだけ。
  - Vercel の Environment Variables
  - GitHub の Actions secrets
  - 本人のパスワード管理の場所（ブラウザやOSのパスワード保存機能など）
- 問い合わせ担当（AI）へは、手順の完了と OK／NG、エラーメッセージだけを伝える。エラーメッセージに秘密情報が含まれていそうなときは、その部分を伏せる。
- 誤って貼ってしまったときの対処: 該当のキーやパスワードを作り直す手順に進む（運用メモ）。
- スクリーンショットで確認を求める手順は作らない。必要な場合は、秘密情報が写らない画面に限定し、そう明記する。
